## Introduction

In special-access programmes (SAPs), including unacknowledged and waived programmes, the goal is not to minimise the number of people with access at any cost. The goal is to ensure that **everyone who must know is included, while everyone else remains outside the compartment**. A well-designed access list is therefore both **small and complete**. It protects exceptionally sensitive information without creating governance failures caused by missing expertise, absent oversight or isolated decision-making.

This distinction matters because modern SAP policy does not treat secrecy as an end in itself. Executive Order 13526 and Department of Defense policy require enhanced protection only where ordinary classification controls are insufficient, while simultaneously establishing oversight structures, access approval processes and [accountability]({{ 'accountability/' | relative_url }}) mechanisms. The practical implementation challenge is deciding which functions genuinely require programme access so that security does not unintentionally remove the very people responsible for testing assumptions, ensuring legality and identifying problems.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://www.cdse.edu/Portals/124/Documents/student-guides/SA001-guide.pdf" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: cdse.edu">[cdse.edu]</a><span class="citation-popover" role="note"><span class="citation-popover-source">cdse.edu</span><span class="citation-popover-snippet">Student Guide Course: Special Access Program (SAP)...February 4, 2020 — Executive Order 13526, “Classified National Security Informa...</span><span class="citation-popover-meta">Published: February 4, 2020</span></span></span>

## Minimum access versus complete access

A common misunderstanding is that "minimum access" means granting access to as few individuals as possible. In practice, SAP policy frames the question differently: access is limited to the minimum number of **personnel necessary** to accomplish programme execution, administration, security and authorised oversight.

That distinction changes how [access lists]({{ 'access-lists/' | relative_url }}) should be designed. A programme with fifty unnecessary members is overexposed. A programme with ten members that excludes essential oversight personnel is incomplete. Both represent poor security design, albeit for different reasons.

A complete access list therefore asks a series of implementation questions rather than pursuing a numerical target:


<div class="content-enhancement content-enhancement--comparison" markdown="1">

* Which personnel are required to execute the programme?
* Which officials must supervise compliance?
* Which specialists are needed to assess technical, operational or legal risks?
* Which authorities require sufficient knowledge to fulfil statutory oversight responsibilities?
* Which personnel should retain access as programmes transition between development, testing and operational use?

</div>

The resulting list may still be very small, but every person included performs a necessary function that cannot reasonably be exercised without programme knowledge. DoD policy similarly ties SAP access to demonstrated need to know, appropriate clearance and programme requirements rather than organisational seniority or curiosity.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://www.esd.whs.mil/portals/54/documents/dd/issuances/dodd/520507p.pdf" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: esd.whs.mil">[whs.mil]</a><span class="citation-popover" role="note"><span class="citation-popover-source">esd.whs.mil</span><span class="citation-popover-snippet">dod directive 5205.07 special access program policy12 Sept 2024 — Establishes policy, assigns responsibilities, and provides governanc...</span></span></span>

## Role-based access for challenge functions

One of the most effective ways to avoid insider [blind spots]({{ 'blind-spots/' | relative_url }}) is to think in terms of **roles** rather than individual personalities. People change jobs, retire or rotate assignments; oversight responsibilities remain.

Challenge functions commonly include:

* **Programme security officers**, who ensure compliance with SAP security procedures.
* **Legal advisers**, who assess statutory authorities, authorities for [intelligence]({{ 'intelligence/' | relative_url }}) activities, contracting issues or international obligations where relevant.
* **Financial and [acquisition]({{ 'acquisition/' | relative_url }}) specialists**, who review expenditure, contracting and procurement decisions.
* **Independent technical experts**, when major engineering or scientific assumptions require external validation.
* **Inspectors, auditors or authorised review bodies**, whose responsibility is independent evaluation rather than programme execution.

These functions do not require unrestricted visibility into every operational detail. Instead, access can be tailored to the information necessary for each responsibility. Someone conducting a financial review may not require operational planning details, while a safety reviewer may need technical data without access to unrelated intelligence sources.

This role-based approach reduces unnecessary exposure while ensuring that no essential governance function disappears simply because everyone outside the operational team lacks programme access.

The structure of current DoD SAP governance reflects this principle by establishing dedicated oversight organisations, central offices and review bodies rather than relying solely on programme managers to supervise themselves.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://www.esd.whs.mil/portals/54/documents/dd/issuances/dodd/520507p.pdf" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: esd.whs.mil">[whs.mil]</a><span class="citation-popover" role="note"><span class="citation-popover-source">esd.whs.mil</span><span class="citation-popover-snippet">dod directive 5205.07 special access program policy12 Sept 2024 — Establishes policy, assigns responsibilities, and provides governanc...</span></span></span>

## Separating operational secrecy from institutional oversight

An important implementation principle is that operational compartmentalisation and institutional oversight solve different problems.

Operational secrecy protects capabilities from foreign intelligence services, adversaries and unauthorised disclosure.

Institutional oversight protects programmes from:


<div class="content-enhancement content-enhancement--caution" markdown="1">

* duplicated effort,
* legal non-compliance,
* excessive costs,
* technical groupthink,
* unmanaged security risks,
* and poor strategic decisions.

</div>

These objectives occasionally appear to compete, but policy attempts to reconcile them through carefully controlled access rather than unrestricted disclosure. Officials responsible for oversight are typically read into programmes through formal approval mechanisms, documented access procedures and programme-specific security obligations instead of receiving broad organisational visibility.

Consequently, enlarging access for narrowly defined oversight purposes is not a failure of compartmentalisation. Properly implemented, it is one of the mechanisms that makes compartmentalisation sustainable over long periods.

## Reviewing who should stay read in

Access lists should not remain static. Personnel changes, organisational restructuring and programme evolution all affect who genuinely requires continued access.

Periodic review helps answer three different questions.

**Should someone be added?** New technical disciplines, emerging legal requirements or changing operational concepts may require expertise that was absent when the programme began.

**Should someone remain?** Personnel who no longer perform relevant duties may no longer satisfy the programme's need-to-know standard, even if they retain an appropriate security clearance.

**Has the programme itself changed?** A capability moving from research into operational deployment may require different oversight, acquisition, testing or sustainment personnel than it did during initial development.

Regular review also limits "access creep", where individuals retain programme knowledge simply because nobody revisits earlier decisions. Maintaining accurate records of indoctrination, [debriefing]({{ 'debriefing/' | relative_url }}) and continuing eligibility supports this process while preserving accountability over who has access at any given time. ## Common implementation failures

Experience reflected in SAP governance reforms suggests that problems often arise from implementation choices rather than from the concept of compartmentalisation itself.

Recurring risks include:

* **Confusing secrecy with effectiveness**, leading to exclusion of legitimate oversight functions.
* **Over-personalising access**, where knowledge follows trusted individuals rather than enduring organisational roles.
* **Failing to reassess access**, allowing outdated lists to persist despite programme evolution.
* **Limiting [internal challenge]({{ 'internal-challenge/' | relative_url }})**, so technical, financial or legal assumptions receive little independent scrutiny.
* **Creating information bottlenecks**, where a handful of individuals become the only route through which essential programme knowledge can pass.

## The practical balance

The central implementation challenge is not deciding between secrecy and oversight but designing access so both remain possible.

For acknowledged, unacknowledged and waived SAPs alike, a well-constructed access list is deliberately selective while remaining functionally complete. Programme personnel, security officers, authorised reviewers and other challenge functions each receive the level of access necessary to perform defined responsibilities—and no more. That approach preserves the security benefits of tight compartmentalisation while reducing the institutional blind spots that can emerge when essential oversight is inadvertently excluded.

    for (var i = 0; i< languages.length; i += 1) {
      var normalized = normalize(languages[i]);
      if (!normalized) continue;
      if (localeMarketMap[normalized]) {
        exactMarket = localeMarketMap[normalized];
        break;
      }
      var languageOnly = normalized.split('-')[0];
      if (!languageMarket && localeMarketMap[languageOnly]) languageMarket = localeMarketMap[languageOnly];
    }
    return { exact: exactMarket, language: languageMarket };
  }
  function inferFromLocale() {
    var matches = localeMatches();
    return matches.exact || matches.language || '';
  }
  function inferFromTimezone() {
    var tz = '';
    try { tz = String(Intl.DateTimeFormat().resolvedOptions().timeZone || ''); } catch (err) {}
    if (!tz) return '';
    for (var i = 0; i< timezoneRules.length; i += 1) {
      var rule = timezoneRules[i] || {};
      try {
        if (new RegExp(rule.pattern).test(tz)) return rule.market;
      } catch (err) {}
    }
    return '';
  }
  function inferMarket(available, options) {
    available = Array.isArray(available) ? available : [];
    options = options || {};
    var storageKey = options.storageKey || 'phoenix-affiliate-market';
    try {
      var saved = window.localStorage && localStorage.getItem(storageKey);
      if (saved && available.indexOf(saved) >= 0) return saved;
    } catch (err) {}
    var timezoneMarket = inferFromTimezone();
    if (timezoneMarket && available.indexOf(timezoneMarket) >= 0) return timezoneMarket;
    var localeMarkets = localeMatches();
    if (localeMarkets.exact && available.indexOf(localeMarkets.exact) >= 0) return localeMarkets.exact;
    if (localeMarkets.language && available.indexOf(localeMarkets.language) >= 0) return localeMarkets.language;
    if (options.defaultMarket && available.indexOf(options.defaultMarket) >= 0) return options.defaultMarket;
    return available[0] || '';
  }

    normalize: normalize,
    inferMarket: inferMarket,
    inferFromLocale: inferFromLocale,
    inferFromTimezone: inferFromTimezone
  };
